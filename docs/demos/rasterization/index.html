光栅化，到底在干什么

一句话：把三角形推到屏幕上，问它盖住了哪些像素。和光线追踪的方向正好相反—— 光栅化以几何为起点，光线追踪以像素为起点。下面每一节都有一个可以动手改的演示， 并且每一节都带一个「常见错误写法」开关：打开它，你会看到那个错误在屏幕上长什么样。

先给结论

光栅化问的是：「这个三角形覆盖了哪些像素？」——以物体为起点，往屏幕推。

光线追踪问的是：「这个像素看到了什么？」——以像素为起点，往场景里追。

方向反过来之后，代价与收益同时反向：

维度光栅化光线追踪
遍历方向三角形 → 像素像素 → 三角形
工作量正比于被覆盖的像素数（与屏幕大小无关）正比于像素数（与屏幕大小成正比）
阴影 / 反射 / 间接光需要额外技术和多趟渲染，天然做不好再发一条光线就行，天然免费
局部性与并行写入连贯、访存友好，硬件流水线极其高效访存散乱、分支发散，靠大规模并行摊平
为什么实时渲染选了光栅化：工作量只看「屏幕上有多少像素被盖住」， 与场景里有多少三角形无关。摄像机拉远，三角形变小，填充成本随之下降—— 这是唯一能在毫秒预算内稳定交付的遍历顺序。代价是它只知道「这一个像素被谁盖住」， 而不知道「这个像素还应该看到什么」。§11 会讲现代渲染器怎么把两者合起来用。

下面左右两边是同一个场景、同一块屏幕、同一份输出图像。唯一差别是到达的方式： 左边以三角形为循环外层，右边以像素为循环外层。注意看两边最后落在缓冲里的像素—— 结果完全一样。

2

三角形与投影：从世界到像素

光栅化只认一种图元：三角形。理由有三条，缺一条它都站不住——

  1. 三点必然共面。四边形及以上不保证共面，不共面就没有唯一的内部插值。
  2. 三点能唯一定义一个仿射插值。平面上的重心坐标唯一，属性沿面插值不会二义。
  3. 任何多边形都能三角化。而三角形的边天然是直线，硬件只需要处理直线。

从世界空间到屏幕像素，要过四道变换。第四道容易被忽略，但它正是 §7 全部麻烦的来源：

世界 → 观察 → 裁剪 → 透视除法 ÷ w → 视口变换 → 像素坐标
观察空间：三角形在三维里，每个顶点带一个 w = −z
屏幕空间：除以 w 之后，三维信息只剩 x/w, y/w, z/w, 1/w

透视除法是唯一不可逆的一步。它把 (x, y, z, w) 压成 (x/w, y/w, z/w) —— 三个数。也就是说，除以 w 之后，屏幕上一个点对「它原来在近处还是远处」只剩下 1/w 这一条线索。 §6 与 §7 两节的全部内容，都是这一条线索的直接推论。

边缘函数与重心坐标

「这个点在不在这条边的内侧？」——这是光栅化里被问得最多的问题。答案只需要一次叉积。 对边 a→b 和点 p：

Eab(p) = (b − a) × (p − a) = (b.x−a.x)(p.y−a.y) − (b.y−a.y)(p.x−a.x)

它的绝对值是两倍的三角形面积 a→b→p，符号则告诉你 p 在边的哪一侧。 于是判定「在三角形内」就是你早就知道的那条规则：

三条边同号 ⇔ 点在三角形内部。这一条对两种绕序都成立—— 顺时针时三个结果全为负，逆时针时全为正，只要同号就在内部，一个 if 都不用加。

真正关键的一步在这里：把三个边缘函数除以它们的和，得到的就是重心坐标。

λ0 = E12 / (E12+E20+E01)　 λ1 = E20 / Σ　 λ2 = E01 / Σ　 Σ = 2·Area
为什么要归一化：和 Σ 就是三角形两倍面积。 不除它，三个边缘函数是「有量纲的面积」，是绝对量；除完之后才是「与位置无关的权重」， 可以直接拿来插值 —— 这一条很重要，因为 §7 的常见错误写法正是忘了除。

覆盖范围收缩：别去测不该问的像素

有了「点在三角形内」的判据，最朴素的做法就是对屏幕上每一个像素都问一遍。 这在 640×320 上已经要问 20 万次，而对一个只盖住 3% 屏幕的三角形来说，其中 97% 是白问的。 硬件当然不这么干，它做两级收缩：

5

填充规则与水密性：为什么共享边是个问题

把两个三角形拼成一个四边形，它们共享一条边。现在设想这条边正好落在像素中心上—— 边界上的这个像素该归谁？

两个都不能选，也两个都不能不选。 如果两个都填，这个像素被写了两次（在开启混合时会重复累积，产生一条亮线）； 如果两个都不填，就会留下一条一像素宽的裂缝，背景从缝里透出来。 只要有一点缝隙，所谓「无缝拼接的网格」就是假的 —— 这就是水密性（watertightness）问题。

工业界的解法是 top-left 规则：把所有三角形的边分成「顶边 / 左边」和「底边 / 右边」两类， 规定边界上的像素只属于顶边和左边。这样任意一条内部边，在它两侧的两个三角形眼里， 必然一个是「左边」另一个是「右边」，于是归属唯一。

一条边是 top 边 ⟺ 它是水平的且指向左（dx < 0）　　屏幕 y 朝下
一条边是 left 边 ⟺ 它不水平且指向下（dy > 0）

深度缓冲：为什么不排序也能画对

有了覆盖判定，下一个问题是遮挡：同一个像素被多个三角形盖住，谁在前面？ 画家算法（先画远的、再画近的）听起来可行，但它解决不了三个情况： 互相穿插的三角形、循环遮挡、以及摄像机一动就要重排。 硬件用的是更笨但更稳的办法：每个像素存一个当前最近深度，画的时候逐个比较。

// 逐像素、逐三角形，顺序无关
if (znew < zbuf[i]) { zbuf[i] = znew; color[i] = shade(...); }

这一句的正确性依赖一个不太显然的事实：深度可以放心地用屏幕空间重心坐标直接线性插值。 推导只有两步：

① 观察空间里，平面上的量沿三角形线性 ⇒ 1/w 在屏幕空间是线性的
② 投影后 zndc = A + B·(1/w) ⇒ zndc 是 1/w 的仿射函数 ⇒ 在屏幕空间也是线性的
结论：深度不需要透视校正，而顶点属性需要（§7）。 这不是「硬件偷懒」，而是数学上恰好成立的 —— 深度和属性在屏幕空间的线性性质根本不同。 把这两件事搞混是这一节最容易犯的错。

透视校正插值：PS1 那种纹理扭动是怎么来的

回到 §3。我们用边缘函数算出的重心坐标 λ，是屏幕空间的权重。 用它插值屏幕上的位置是绝对正确的 —— 但用它插值世界空间的量（纹理坐标、法线、颜色）， 就是错的。原因藏在 §2 那一步透视除法里。

屏幕空间线性的是 attr / w 和 1 / w，不是 attr 本身。
错误　attr = λ0·attr0 + λ1·attr1 + λ2·attr2　　（仿射插值）
正确　λ′i = (λi / wi) / Σ(λj / wj)　→　attr = Σ λ′i·attri
等价的说法（硬件实际做的事）：把 attr/w 和 1/w 两个通道都用屏幕空间重心坐标插值，最后相除。所以透视校正的成本是每个属性多一个通道， 而不是多一次除法 —— 这也是为什么它便宜到所有 GPU 都默认开启。

背面剔除：判据必须取在屏幕空间

封闭模型的背面永远不会被看到 —— 除非模型破了、或者材质是半透明的。 所以先扔掉背向摄像机的三角形，能省下大约一半的片元。判据是屏幕空间的有符号面积：

area2(v0,v1,v2) = E01(v2)　 屏幕空间三角形的两倍有符号面积
正面 ⇔ area2 的符号 = 该 API 的 frontFace 约定

它比「算法线再点乘」更可靠的地方在于：这个判别必须发生在所有变换之后。 投影会翻转一次手性，视口变换里 y 轴朝下又翻转一次，模型矩阵还可能带负缩放。有符号面积是变换之后的几何量， 把这一串符号全都自动包含了进去。

三种教科书级的翻车方式，这一节都能打开看： ① 用物体空间的绕序判朝向 —— 模型一转，判据不跟着变，于是「背面」永远不变； ② frontFace 约定与网格绕序不一致 —— 整个模型内外面颠倒，看到的是内壁； ③ 网格里某个面的绕序写反了 —— 剔除后那个面直接消失，从外面能看进去。 第 ③ 种最隐蔽：不开剔除时完全正常，一开剔除就少一块， 而这正是网格数据问题最常见的暴露方式。

着色频率：Flat / Gouraud / Phong

光栅化有两个可编程阶段：顶点着色器（每个顶点跑一次）和片元着色器（每个像素跑一次）。 同一套光照公式放在哪一边，决定了画面质量与成本。三种经典做法：

模式顶点阶段做片元阶段做特征
Flat不算光照，只传面法线用面法线算一次每个三角形一个色块
Gouraud算光照，传顶点颜色插值颜色高光会被「抹平」，出现 Mach band
Phong只传顶点法线算光照（用插值后的法线）高光正确，成本随像素数走

Gouraud　color = Σ λi · shade(Ni)　　// 光照在顶点阶段算，颜色线性插值

抗锯齿：MSAA 与 SSAA 差在哪

光栅化的覆盖判定是硬判决：像素中心在三角形内就整个像素着色，不在就完全不管。 于是斜边会变成台阶 —— 这就是锯齿。最直接的解法是超采样（SSAA）： 渲染到 4 倍分辨率再缩回来。它有效，但成本也 4 倍。

多重采样（MSAA）换了个思路：只让「覆盖」和「深度」变成多采样，着色仍然每像素一次。 每个像素取 N 个子采样点，每个点有独立的覆盖标记与深度；片元着色只做一次， 结果写进所有被覆盖的子采样；最后按覆盖率把 N 个值平均。

SSAA　着色次数 = 像素数 × N　　每个子采样都算一遍光照
MSAA　着色次数 = 像素数　　只算一次，靠覆盖率做边缘平均
MSAA 只在几何边缘有效，对纹理内部的高频没有作用—— 因为采样点只用来判覆盖，颜色还是每像素一次。所以 MSAA 几乎免费地解决了锯齿边缘， 却完全解决不了「远处棋盘格闪烁」。后者需要 mipmap 或者时域抗锯齿（TAA）。

为什么真实硬件还要「质心采样」：本页的实现是在像素中心着色， 但如果像素中心恰好落在三角形外面（边缘像素很常见），在那里取重心坐标就等于外推—— 属性会被算到三角形之外去。硬件的做法是把着色位置挪到这个像素被覆盖区域的质心上（centroid）。 代价是相邻像素的着色位置不再等距，某些导数类运算（比如 mipmap 的 LOD 选择）会出现瑕疵。 这是 MSAA 与「纹理采样」之间一个真实存在的工程摩擦点。
11

两条路的合流：现代渲染器的实际形态

走完这十节，结论不是「光栅化赢了」或「光线追踪赢了」，而是两者各自守着对方做不到的那件事：

要解决的问题谁做得好为什么
主可见性（第一个交点）光栅化深度缓冲一趟扫过去，写入连贯、并行度极高
阴影（任意光源）光线追踪阴影贴图的分辨率与视锥都是妥协，光线查询是精确的
镜面反射 / 折射光线追踪SSR 只能反射屏幕里已有的东西，屏幕外就没了
全局光照 / 间接光光线追踪光栅化没有「从别处来的光」这个概念
高频细节可见性光线追踪它按几何求交，不受采样像素密度限制

所以现代实时渲染器的实际形态是混合管线：

光栅化 pass → 写出 G-Buffer（深度 / 法线 / albedo / 粗糙度 / 运动矢量）
↓ 光追 pass 在 G-Buffer 上发次级光线（阴影 / 反射 / AO / GI）
↓ 时域累积（复用上一帧结果，压低采样数）
↓ 合成 + 后处理
G-Buffer 是两条路的接口：光栅化把「这个像素的表面信息」写下来，光追拿它当起点
为什么时域累积是必须的：§1 说过，光线追踪的成本随采样数走。 要在 2 ms 内做完阴影、反射和一路间接光，每像素能负担的光线数是个位数。 解法是「每帧只发少量光线、跨帧累积」——代价是运动时的拖影， 所以需要运动矢量和历史校验来抑制。这条路线正是 AlphaEngine 的 dual-tier ray tracing + temporal radiance feedback 要处理的核心问题。
不归一化重心坐标

直接用边缘函数值当权重，插值结果随三角形面积整体缩放。
