# 路径追踪与蒙特卡洛积分

> [!abstract] 一句话结论
> 路径追踪不从光源发光，而是**从相机反向追光路**，用**蒙特卡洛采样**估计渲染方程。`ray_color(r)` 的返回值始终是同一个量：**从方向 `r` 入射到 `r` 起点的光量**。递归不是"交点发光"，而是"换到交点、继续追问光的来源"。

## 1. 反向追踪

### 1.1 为什么不用正向

真实光路是「光源 → 表面 → 表面 → … → 相机」。但从光源出发的光线**绝大多数永远打不到相机**——一个像素占整幅画面的立体角可能只有 1e-8，发一亿条光线也可能一条都没命中。正向追踪的采样效率是数量级上的死路。

### 1.2 光路可逆

反向追踪之所以成立，靠的是 **Helmholtz 互易性（光路可逆）**：

```
"天空 → P → 相机"  这条光路携带的光量
          ＝
"相机 → P → 天空"  这条光路携带的光量
```

同一条折线反着走，光量不变。所以从相机出发、每个像素只发一条光线，结果与从光源出发完全一致——但效率高出若干数量级。

> [!important] 关键区分
> 反向意味着**起点是相机、终点是光源**。递归中的每一步都不是"发光"，而是"查询"：*那个方向有多少光？*

### 1.3 递归的语义

`ray_color` 的返回值始终是同一个量：**从光线方向入射到光线起点的光量**（记作 `L_in`）。两个出口与之一致：

| 分支 | 含义 | 返回 |
|---|---|---|
| 未命中 | 该方向的入射光来自天空 | 天空亮度 |
| 命中 | 该方向的入射光来自**那个表面的反射** | `albedo × (该表面接收到的光的平均)`，递归求 |

所以整条递归是一条**追问链**：

```
这个方向有多少光？
  → 那里有个球面 → 球面反射了多少？
    → 取决于它接收到的光 → 那些光从哪来？
      → 天空，或另一个表面 → 继续追问 …
```

**球面不是被"绘制"的对象，而是一个无状态的查询函数。** 形状全部编码在求交代数里；相机不问，它就不存在。这也是表面"一直是对的"的原因——每次调用都从几何定义重算，没有可累积的状态、没有一致性需要维护。

## 2. 蒙特卡洛估计

### 2.1 漫反射的半球积分

Lambertian 表面的出射光是对**整个半球**入射光的积分：

```
L_out(P) = (albedo/π) · ∫ L_in(ω) · cosθ dω
```

该积分对复杂场景没有解析解，必须用**蒙特卡洛**：随机撒 N 个方向、取平均。通用形式（含重要性采样）：

```
L_out ≈ (albedo/π) · (1/N) Σ [ L_in(ωᵢ) · cosθᵢ / p(ωᵢ) ]
```

### 2.2 余弦加权采样让权重自动抵消

`rec.normal + random_unit_vector()` 生成的方向恰好服从**余弦分布** `p(ω) = cosθ/π`。代入上式：

```
= (albedo/π) · (1/N) Σ [ L_in(ωᵢ) · cosθᵢ / (cosθᵢ/π) ]
                          ↑ cosθ 与 π 完全约掉
= albedo · (1/N) Σ L_in(ωᵢ)
```

**估计器化简成最简单的平均值。** 这就是那句看似随意的 `normal + random_unit_vector()` 在数学上讲究的原因——它让权重自动配平。

### 2.3 代码与公式逐项对应

| 公式 | 代码 |
|---|---|
| `1/N` | `pixel_sample_scale = 1.0 / sample_per_pixel` |
| `Σ L_in(ωᵢ)` | `pixel_color += ray_color(...)` |
| `albedo` | `0.5` |
| `L_in`（递归求） | `ray_color(下一条光线, depth - 1, world)` |
| 余弦加权采样 `ωᵢ` | `rec.normal + random_unit_vector()` |

**采样循环字面上就是那个估计器，`N = 100`。**

## 3. 递归的具体形态

### 3.1 线性递归，不是树

```cpp
return 0.5 * ray_color(ray(rec.p, direction), depth - 1, world);
//           ↑ 只有这一处递归调用
```

每次只调用自己一次，展开是一条**链**。调用数线性（≤ `max_depth + 1` 次），不是指数级——若此处写成两次递归调用，50 层就是 2⁵⁰，完全跑不动。

### 3.2 两个终止条件，作用完全不同

| 终止条件 | 触发场景 | 返回 | 性质 |
|---|---|---|---|
| `world.hit(...) == false` | 光线逃逸到天空 | 背景色 | **正常出口**，绝大多数路径走这里 |
| `depth <= 0` | 弹射 `max_depth` 次仍未逃逸 | `(0,0,0)` | **保险丝**，防止无限递归爆栈 |

第二个是必须的：光线可能被"困"在几何体之间来回弹射。

### 3.3 衰减与有效弹射次数

```
最终颜色 = albedoⁿ × 天空色          n = 逃逸前的命中次数
```

| 弹射次数 n | 系数（albedo = 0.5） | 可见性 |
|---|---|---|
| 0 | 1.0 | 直接看到天空 |
| 1 | 0.5 | |
| 5 | 0.031 | 很暗 |
| 10 | 9.8e-4 | 几乎不可见 |
| 50 | 8.9e-16 | 等于黑 |

**实际有效路径不超过约 10 次弹射**，深度耗尽分支的贡献小到看不见。

### 3.4 等价循环写法

因为是链式递归，可以直接改写成循环——结果逐位相同，但不用压几十层栈，也更接近加入材质系统后的真实渲染器写法：

```cpp
color ray_color(const ray& r, const hittable& world, int max_depth) {
    color attenuation(1, 1, 1);   // 累积衰减，对应递归里的 albedoⁿ
    ray   current = r;

    for (int d = 0; d < max_depth; d++) {
        hit_record rec;
        if (!world.hit(current, interval(0.001, infinity), rec))
            return attenuation * sky_color(current.direction());   // 逃逸
        attenuation *= 0.5;                                         // 等价于每层乘 albedo
        current = ray(rec.p, rec.normal + random_unit_vector());
    }
    return color(0, 0, 0);                                          // 深度耗尽
}
```

## 4. 边界与陷阱

- **"交点发光"是误解。** 递归不产生光，只查询光。混淆这两者，在做直接光采样 / NEE 时会彻底找不到北。
- **`normal + random_unit_vector()` 可能接近零向量。** 当随机方向恰好接近 `-normal` 时，和向量长度趋近 0。后果：`unit_vector` 内的 `near_zero` 断言可能触发；求交里 `a = D·D ≈ 0` 会让 `t` 爆成巨大值。需要显式处理退化方向。
- **`t_min` 的语义依赖方向是否归一化。** 方向由 `normal + random_unit_vector()` 给出时长度在 0～2 之间，`interval(0.001, ...)` 中的 `0.001` 是 `t` 而非距离，实际推开的距离随方向浮动。
- **凸体不自遮挡，但会互相照亮。** 球面上一点发出的半球方向不会再打回自身（凸性），但仍可能打到地面再弹回球面——递归自然捕捉了这条间接光路。真实渲染器要专门的全局光照方案，路径追踪用递归免费拿到，代价是噪声。
- **噪声幅度约 `σ/√N`。** 单次路径的结果毫无意义，正确性来自大量独立同分布样本的平均。`N = 100` 时噪声约为单次标准差的 1/10。
- **相邻像素共享法线，因此画面平滑。** 球面连续 → 相邻像素的交点与法线几乎相同 → 采样同一个半球分布 → 期望值几乎相同。**平滑来自几何连续性，噪声来自统计涨落，两者来源不同。**

## 5. 在渲染器中的落点

### 5.1 起点状态（RTIOW 第九章阶段）

本笔记首次记录时，`Engine/` 的实现有三个特征：

1. **场景没有独立光源** —— 唯一的颜色来源是天空背景。所有可见颜色（球、地面）都是**天空色的缩放**，色调完全由天空决定
2. **`albedo` 硬编码为标量 `0.5`** —— 对球和地面相同、且无彩色。标量乘 `vec3` 是等比例缩放，**只能调明暗、调不了色调**
3. **材质尚未抽象** —— 所有表面共用同一个 `0.5 *`，无法逐物体设置外观

### 5.2 当前状态（RTIOW 13.x 阶段，2026-09-21 复核）

对照上述三点，**第 2、3 点已被解决，第 1 点仍成立**：

1. **反射率已由材质携带** —— `hit_record` 增 `shared_ptr<material> mat`，`ray_color` 改为

   ```cpp
   ray scattered;
   color attenuation;
   if (rec.mat->scatter(r, rec, attenuation, scattered)) {
       return attenuation * ray_color(scattered, depth - 1, world);
   }
   return color(0,0,0);
   ```

   标量 `0.5 *` 已消失，物体第一次拥有自己的颜色与散射行为。已落地的材质为 `lambertian`（朗伯漫反射）、`metal`（镜面 + `fuzz`）、`dielectric`（折射 + Schlick 近似反射率），即漫反射、镜面、折射三类散射路径齐备。
2. **场景仍无显式光源** —— 唯一的颜色来源依旧是天空背景，因此画面色调仍由天空主导。这是当前噪声水平与着色能力的主要瓶颈，也是下一步引入直接光采样（NEE）的动因。
3. **截断仍为固定深度** —— `max_depth` 到顶即返回黑色，尚无俄罗斯轮盘赌，因此长路径被系统性截断（性质差异见第 3 节）。
4. **随机源已显式化，采样与调度开始解耦** —— 全局 `random_double()` 被替换为显式注入的 `rng_t` 上下文（`mt19937` + 均匀分布），沿场景构建 → `get_ray` → `material::scatter` → 递归全程传递；渲染改为多线程按行分块，每线程持有独立引擎，先写入帧缓冲再顺序输出 PPM。

> [!important] 线程化与蒙特卡洛前提的关系
> 第 2 节的估计器前提是**大量独立同分布样本**。线程化不破坏这一点：同一像素的 `N` 个样本仍由同一条工作线程按序产生，像素之间互不共享随机序列，因此无偏性与 `σ/√N` 的方差结论都不受影响。
> 受影响的只有**可复现性**：种子当前按「线程序号」派生，噪声图案会随线程数（即机器核数）变化。若需要跨机器逐像素可复现，应把种子改为按**行号或像素坐标**派生——这同时也是把静态分块改为动态调度的前提，否则调度顺序会重新引入不确定性。

> [!note] 本次复核只更新对仓库的观测
> 上文推导结论不变，变的是实现状态。对应 [[10-Outcomes/10-AlphaEngine#实现现状（学习性过渡基线）|实现现状]]。

### 5.3 演进方向

| 改动 | 效果 | 状态 |
|---|---|---|
| `0.5 *` → `attenuation *`（材质携带的 `vec3`） | 物体第一次拥有自己的颜色 | ✅ 已落地（`b7256ec`） |
| 用 `operator*(const vec3&, const vec3&)`（Hadamard 积） | 逐通道反射率，即 albedo × 光强 | ✅ 已落地 |
| 加入显式光源与直接光采样 | 摆脱"天空是唯一光源"的限制，同时降低方差 | ⏳ 未开始 |
| 显式光源下必须处理"命中光源"分支 | 否则光源本身不可见 | ⏳ 待显式光源引入后处理 |
| 引入俄罗斯轮盘赌 | 替代固定 `max_depth`，在不引入偏差的前提下截断长路径 | ⏳ 未开始 |

> [!note] 与 `vec3` 设计的呼应
> `vec3` 里的分量乘 `operator*(const vec3&, const vec3&)` 之所以存在，正是为了让 albedo 能逐通道作用于入射光。它是光传输代码里最常用的运算符，不是冗余设计。
